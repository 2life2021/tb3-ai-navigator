## 2. パラメータの分類：何が「学習」され、何を「人間」が決めたか

本作品で**学習によって決まる値は、MLPの重みとバイアス（26,243個）だけ**です。それ以外はすべて人間が決めた値（ハイパーパラメータ・設計値）で、すべてコード上の定数またはコマンドライン引数として記録されています。

### 2.1 タスク・ロボットの設計値（`scripts/common.py`）
| 名前 | 値 | 意味 |
|---|---|---|
| `RANGE_MAX` | 3.5 m | 正規化と、inf の置き換えに使う最大距離 |
| `ACTIONS` | FORWARD / LEFT / RIGHT | 行動クラス（出力の次元 = 3） |
| `ACTION_TWIST` | 前進 (0.18, 0) ／ 左 (0.02, +0.9) ／ 右 (0.02, −0.9) | 各行動の (v [m/s], ω [rad/s])。**開発の全期間を通して変更していない** |

### 2.2 教師ルールの閾値（ラベルの定義そのもの）
| | 教師 v1 `teacher_action_v1` | 教師 v2 `teacher_action_v2` |
|---|---|---|
| 前方の範囲・閾値 | ±25°、> 0.55 m | ±30°、> 0.55 m |
| 斜め前の範囲・閾値 | 25〜60°、> 0.30 m | 30〜75°、> 0.35 m |
| 真横の確認 | なし | 75〜105° が 0.22 m 未満なら、反対側へ旋回 |
| 旋回方向の決め方 | 20〜100° の平均距離が大きい側（同じ値なら左） | 同じ |

※ `common.py` の `teacher_action` は、現在 `teacher_action_v2` を指しています。`collect_data.py` で今データを集めると、ラベルは v2 になります。

### 2.3 特徴量
| 名前 | 値 | 備考 |
|---|---|---|
| セクタ数 | 24（v1 系）／ 72（v2_s72・v2_aug） | チェックポイントの `n_sectors` に保存される。v1 系のチェックポイントにはこの値がなく、既定の 24 として読み込まれる |
| セクタの配置 | 24: 正面を中心に ±7.5°（オフセットあり）／ 72: 0°から5°刻み（オフセットなし） | `scan_to_features` |
| 集約方法 | セクタ内の最小値を 3.5 で割る | |

### 2.4 データ収集（`collect_data.py`）
| 名前 | 値 |
|---|---|
| `--epsilon` | ランダム行動を始める確率。行動は 1〜4 ステップ続ける |
| `--beta` | DAgger のとき、教師が操作する確率 |
| `--duration` | 収集時間（**実時間**。シミュレーション時間ではない） |
| `STUCK_DIST` | 0.13 m。これより近づいたら `/reset_world` |
| 立ち往生の判定 | 15 秒間の移動が 0.10 m 以下なら `/reset_world` |
| リセット後の待機 | 2 秒間は再リセットしない |
| **保存されるラベル** | 実際に実行した行動ではなく、**常にその時点の教師ルールの出力** |

### 2.5 学習（`train.py`）
| 名前 | 値 | 備考 |
|---|---|---|
| 隠れ層の幅 `--hidden` | 64（v1・DAgger）／ 128（v2 系） | 隠れ層は 2 層で固定（`PolicyMLP`） |
| エポック数 `--epochs` | 300 ／ 600 ／ 150 | 下の表を参照 |
| バッチサイズ | 128 | コード中に固定 |
| 最適化 | Adam、lr=1e-3、weight_decay=1e-4 | コード中に固定 |
| 損失 | クラス重み付き交差エントロピー。重み = 総数 /（3 × 各クラスの数）を**学習側のラベル**から計算 | |
| 検証データの分割 | 無作為に 20%（`int(N×0.2)`）、乱数シード `--seed 0` | 同じデータ・同じシードなら同じ分割になる |
| データ拡張 `--augment` | 0 ／ 4 | 1サンプルにつき、左右反転1個＋ノイズ付き（σ=0.02 m）4個×(元, 反転) で、合計 9 個を追加。学習側のみ |
| 再ラベル `--relabel` | あり／なし | 生LiDAR (`raw`) から、現在の `teacher_action` でラベルを付け直す |

### 2.6 推論・制御（`ai_driver.py`）
| 名前 | 値 |
|---|---|
| 推論のタイミング | `/scan` を受信するたび（約 5Hz）。タイマーは使わない |
| `--control` | `argmax`（既定）／ `soft`（確率で v, ω を重み付け平均） |
| PyTorch のスレッド数 | 1（`policy.py` で設定） |

### 2.7 評価（`ai_driver.py`、`eval_all.sh`）
| 名前 | 値 |
|---|---|
| `COLLISION_DIST` | 0.13 m（LiDAR 全周の最小値がこれ未満になった回数を「衝突イベント」として数える） |
| 走行距離 | `/odom` の位置変化を積算する。1回の変化が 0.5 m 以上の場合（リセットによるジャンプ）は除外 |
| 試行時間 | 90 秒（一括評価）／ 120 秒（予備評価）／ 150 秒（デモ）。**すべて実時間**。シミュレーションの実時間比は記録上 0.94〜0.98 |
| 試行回数 | 各条件 3 回（一括評価） |

## 3. データの来歴：どの教師が、どの条件で集めたか

| データ | 運転していたもの | 保存されたラベル | ε | β | 時間 | サンプル数 | ラベル分布 (前/左/右) | リセット回数 | 開始位置 |
|---|---|---|---|---|---|---|---|---|---|
| `teacher.npz` | 教師 v1（ε でランダム行動） | 教師 v1 | 0.10 | – | 240 s | 1,176 | 1020 / 85 / 71 | 0 | **記録なし**（手動操作のあとの位置から） |
| `dagger1.npz` | `policy.pt`（v1 モデル）、確率 β で教師 v1 | 教師 v1 | 0.05 | 0.3 | 180 s | 863 | 721 / 84 / 58 | 0 | **記録なし**（直前の走行の終了位置から） |
| `teacher_v2.npz` | 教師 v2（ε でランダム行動） | 教師 v2 | 0.10 | – | 240 s | 1,167 | 717 / 233 / 217 | 1 | **記録なし**（直前の評価の終了位置から） |

- 3つのファイルとも、`X`（収集時の24セクタ特徴量）、`y`（その時点の教師のラベル）、`raw`（inf を 3.5 m に置き換えた360本の距離）を保存しています。
- **v2 系のモデルはすべて `--relabel` で学習しています**。つまり、`teacher.npz` と `dagger1.npz` に保存された v1 のラベルは使わず、`raw` から教師 v2 でラベルを付け直しています。
- **最終採用モデル `policy_v2_aug.pt` の学習データには、DAgger で集めた状態（v1 モデルが運転したときの状態 863 件）が、教師 v2 のラベルで含まれています**。つまり、DAgger は「v1 ラベルのまま追加学習した」条件では走行を悪化させましたが、その状態データ自体は最終モデルに使われています。DAgger の状態データが最終モデルの性能にどれだけ寄与したかは、切り分けて評価していません。

## 4. モデルの来歴

| モデル | データ | 再ラベル | セクタ | 隠れ層 | エポック | 拡張 | 学習精度 | 検証精度 | 状態 |
|---|---|---|---|---|---|---|---|---|---|
| `policy.pt` (v1) | teacher | なし（v1ラベル） | 24 | 64 | 300 | 0 | 96.8% | 91.1% | 公開 |
| `policy_dagger1.pt` | teacher + dagger1 | なし（v1ラベル） | 24 | 64 | 300 | 0 | 98.7% | 93.9% | 公開 |
| 最初の `policy_v2.pt` | teacher_v2 のみ | なし（v2ラベル） | 24 | 64 | 300 | 0 | 91.4% | 79.0% | **上書きされて現存しない**（数値は実行時の出力記録による） |
| `policy_v2_s24.pt` | 3データ | v2 | 24 | 128 | 600 | 0 | 98.4% | 87.1% | 公開 |
| `policy_v2_s72.pt` | 3データ | v2 | 72 | 128 | 600 | 0 | 99.8% | 88.3% | 公開 |
| **`policy_v2_aug.pt`** | 3データ | v2 | 72 | 128 | 150 | 4 | 95.9% | 87.2% | **最終採用**・公開 |

- 学習精度は、拡張を含む学習側データに対する精度です。
- 「3データ」= `teacher.npz` + `dagger1.npz` + `teacher_v2.npz`（合計 3,206 件。うち検証 641 件、学習 2,565 件）。
- v2_s24、v2_s72、v2_aug は同じデータ・同じシードなので、**検証データの641件はまったく同じ**です。これら3つの検証精度は、同じ問題に対する比較になっています。v1 と DAgger は検証データが異なるため、直接比較できません。

### 学習の決定性（再現性の証拠）
上書きされた2つ目の `policy_v2.pt`（`--relabel --hidden 128 --epochs 600`、24セクタ）と `policy_v2_s24.pt` は、間に `train.py` の改修（特徴量を `raw` から計算し直す変更など）を挟んで別々に学習しました。それでも、記録された**学習精度 0.98441 と検証精度 0.87051 が完全に一致**しています（`models/policy_v2_metrics.json` は非公開、`policy_v2_s24_metrics.json` は公開）。このことから、少なくともこの環境では、同じデータ・同じ設定・同じシードで学習すれば同じ結果が得られると考えられます。ただし、異なるCPUやPyTorchのバージョンで同じ結果になるかは確認していません。

## 5. 何が再現でき、何が再現できないか

| 対象 | 再現性 | 理由 |
|---|---|---|
| 学習（同じ npz から） | **高い** | numpy と PyTorch のシードを固定している。上の一致例がある |
| データ収集 | 低い | `random` のシードを固定していない。LiDAR ノイズ、通信のタイミング、開始位置（記録なし）によって変わる |
| 走行評価 | 中程度 | 開始位置は `/reset_world` でそろえた（12回中10回成功）。ノイズとタイミングによって軌跡は毎回変わる。yaw は記録していない |
| 実行時間 | 注意が必要 | すべて実時間で区切っている。シミュレーション速度が変わると、同じ「90秒」でも走行内容が変わる。実際に一度、scan が約 0.9Hz に低下した走行（run_20261101_101906）があった |

### 各モデルを再現するコマンド
```bash
# v1（保存されている v1 ラベルをそのまま使う。--relabel を付けないこと）
python3 scripts/train.py data/teacher.npz --out models/policy.pt
# v1 + DAgger
python3 scripts/train.py data/teacher.npz data/dagger1.npz --out models/policy_dagger1.pt
# v2_s24 / v2_s72
python3 scripts/train.py data/teacher.npz data/dagger1.npz data/teacher_v2.npz --relabel --sectors 24 --hidden 128 --epochs 600 --out models/policy_v2_s24.pt
python3 scripts/train.py data/teacher.npz data/dagger1.npz data/teacher_v2.npz --relabel --sectors 72 --hidden 128 --epochs 600 --out models/policy_v2_s72.pt
# 最終モデル
python3 scripts/train.py data/teacher.npz data/dagger1.npz data/teacher_v2.npz --relabel --sectors 72 --augment 4 --hidden 128 --epochs 150 --out models/policy_v2_aug.pt
```
- v1 系のデータを**新しく集め直す**場合は、`common.py` の `teacher_action = teacher_action_v2` を `teacher_action_v1` に変える必要があります。v1 データの収集時には、この行は存在せず、`teacher_action` が v1 そのものでした。

## 6. 再現性を高めるために足りないもの（未実施）
1. データ収集の開始位置・yaw と、乱数シードの記録
2. 走行評価での yaw の記録と、リセット成否の確認
3. 実時間ではなくシミュレーション時間（`/clock`）で試行時間を区切る
4. モデル・ログのファイル名に日時や設定を含め、上書きを防ぐ
