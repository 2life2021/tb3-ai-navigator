# 開発記録 — 問題 → 原因 → 修正 → 確認

開発中に起きた問題と、その対処を時系列でまとめます。「原因」は、ログや実行結果で**確認できたもの**と、**推定にとどまるもの**を区別して書いています。根拠となる記録（ログファイル名、メトリクス）も併記します。

---

## A. 学習・推論・制御に関わる変更

| # | 起きた問題（観測） | 原因 | 修正 | 確認 |
|---|---|---|---|---|
| A1 | 環境の調査で、`teleop_keyboard` が `/cmd_vel` にゼロ速度を 10Hz で送り続けていた | **確認済み**: `ros2 topic hz /cmd_vel` で 9.9Hz、送信元は teleop の1つだけだった。AI の指令と競合する | 了承を得て teleop を停止した（Gazebo は停止していない） | 停止後は `/cmd_vel` に流れているメッセージがないことを確認した |
| A2 | v1+DAgger の最初の評価で衝突イベントが12回あった。ただし v1 とは開始位置が違っていた（`run_095920` は (-1.76, -0.43) から、`run_095319` は (-0.55, 0.76) から） | **確認済み**: 各試行が前回の終了位置から始まるため、比較条件がそろっていなかった | `ai_driver.py` に `--reset`（開始時に `/reset_world`）を追加した | 以後の試行は (-2.0, -0.5) から開始した（一括評価では12回中10回） |
| A3 | `--reset` を付けると `AttributeError: 'AIDriver' object has no attribute 'start'` で落ちた | **確認済み**: `__init__` の中でサービスの応答を待つ `spin_until_future_complete` を呼んだため、すでに登録済みだった `/scan` のコールバックが、初期化の途中で実行された | リセット処理を、購読（`create_subscription`）より前に移した | 再実行で正常に動作した |
| A4 | 開始位置をそろえても、v1+DAgger は衝突イベント6回（v1 は0回）。検証精度は v1 より高かった（93.9% 対 91.1%） | **推定**: 教師 v1 が真横を見ていないため、障害物の近くで「前進」を正解とするラベルが、DAgger で増えた近距離の状態データによって強化された（ログには障害物の方向がないため未検証。各1回の比較） | 教師ルールに真横の確認を加えた教師 v2 を作った（`teacher_action_v2`） | 教師 v2 単体の走行で、最接近距離 0.198 m → 0.234 m（各1回） |
| A5 | 教師 v2 のデータ（1,167件）だけで学習した最初の v2 モデルは、検証精度 79.0%（学習 91.4%）だった | **推定**: v2 はラベルの判断が細かく、旋回クラスが増えて難しくなったのに対して、データ量（約1,100件）と隠れ層の幅（64）が足りなかった | 過去の全データ（3,206件）を `raw` から教師 v2 で再ラベルし（`--relabel` を新設）、隠れ層を128に、エポック数を600にした | 検証精度 87.1%（`policy_v2_s24`） |
| A6 | 同じ最初の v2 モデルの走行は、`--duration 120` なのに 290.8 秒かかり、scan の受信は252回（約0.9Hz）、走行距離は6.4mだった（`run_101906`） | **未解明**: 直後に計測した `/scan` は 4.86Hz で正常だった。一時的なホストの負荷が考えられるが、原因は特定できていない | 予防策として、推論側の PyTorch を1スレッドにした（`torch.set_num_threads(1)`）。効果は検証していない | 以後の走行では同じ現象は起きていない（scan はどの回も約 4.8Hz） |
| A7 | 24セクタでの検証精度が約87%で頭打ちになり、学習精度98%との差が大きかった | **推定**: 教師の角度境界（30°・75°・105°）と、15°セクタの境界（22.5°、37.5°…）がずれているため、同じ特徴量に異なるラベルが付く状態が生じる | 5°刻みの72セクタを追加した（`--sectors 72`）。境界が5°の倍数になり、教師の角度とそろう | 検証精度 87.1% → 88.3%（同じ検証データ）。改善はわずかだった |

### 推論方法の変更で、制御部分が変わったかどうか
- 行動ごとの速度 `ACTION_TWIST` は、最初から最後まで変えていません。
- 一括評価の後に `ai_driver.py` に加えた変更は、可視化用のトピック `/ai_nav/probs` の送信、未使用 import の削除、docstring の修正だけです。行動の決定と速度指令の計算は変わっていません。

| B1 | AI視点モニターに確率が届かない（"waiting for /ai_nav/probs"） | **推定**: ドライバ（root）とモニター（ubuntu）の間で、FastDDS の共有メモリ通信がユーザー権限の違いにより失敗した。同じユーザーで起動したら解消したので、可能性は高い | 両方を同じユーザー（root、X の認証ファイルを指定）で起動する。README に注意を記載した |

## C. この記録から得た学び
1. **オフラインの検証精度と、閉ループの走行性能は別物**: 検証精度が最も高かった v1+DAgger（93.9%）が、走行では最も悪かった（A4）。逆に、データ拡張は検証精度を上げなかったが、走行では障害物から距離を保つようになった（A9）。
2. **比較条件をそろえることの難しさ**: 開始位置（A2、A11）、評価指標の基準（A12）、シミュレーション速度（A6）など、気づかないうちに条件が変わる要因が多くあった。どれも「ログに残していたから後で気づけた」ものである。
3. **ラベルの定義こそが最も重要なハイパーパラメータ**: 教師の閾値は学習されない人間の設計であり、モデルの振る舞いを直接決める（A4、A7）。生データ（`raw`）を残しておいたことで、ラベルの定義を変えても再走行せずに済んだ（A5）。
4. **成否を確認しないコードは、失敗を見えなくする**: `/reset_world` の成否を確認していなかったため、失敗に後から気づいた（A11）。同様に、ログを絞って表示していたため（`grep summary`）、失敗の原因も追えなかった。
